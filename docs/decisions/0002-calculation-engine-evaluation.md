# ADR-0002 — 한국 출생 범위와 계산 엔진 검증

작성일: 2026-09-11

상태: **한국 출생자 우선 지원 확정 / iztro 운영 채택 보류**

## 결정과 근거

첫 출시는 한국 출생자를 지원한다. 해외 출생 지역 선택은 첫 입력 화면에 추가하지 않는다. 지원 연도와 역사적 표준시·서머타임 보정은 아직 확정되지 않았다.

기존 iztro API와 설정, 타입, 라이선스를 먼저 조사하고 실제 패키지로 검증했다. `iztro@2.6.1`과 비교용 `korean-lunar-calendar@0.4.0`은 모두 MIT이며 평가 테스트에만 사용하는 개발 의존성이다. 앱 계산 경로에는 아직 연결하지 않는다. 한국 달력 패키지는 한국천문연구원이 배포·인증한 SDK가 아니다.

**iztro의 음력을 한국 음력으로 간주할 수 없다.** 한국천문연구원은 2012년 한국은 윤3월, 중국은 윤4월이며 음력 4월 8일이 각각 양력 5월 28일과 4월 28일이라고 설명한다. 패키지 비교에서도 이 차이가 재현된다.

| 입력 또는 변환             | 한국 달력 패키지 | iztro         |
| -------------------------- | ---------------- | ------------- |
| 음력 2012-4-8, 평달 → 양력 | 2012-5-28        | 2012-4-28     |
| 양력 2012-5-28 → 음력      | 2012-4-8 평달    | 2012-4-8 윤달 |
| 양력 2017-6-24 → 음력      | 2017-5-1 윤달    | 2017-6-1 평달 |

한국 음력을 양력으로 바꾸고 iztro에 전달해도, 내부 계산은 iztro의 달력으로 진행한다. 이 방법만으로 한국 음력 기반 명반이 구현되는 것은 아니다. 한국 출생자 지원이라는 결정과 명반 배치에 사용할 음력 기준은 구분해야 한다.

출처: [한국천문연구원 2012년 천문현상 예보](https://www.kasi.re.kr/kor/publication/post/newsMaterial/2444), [한국 달력 패키지 원문·2017년 예제](https://github.com/usingsky/korean_lunar_calendar_js).

## 확인한 API와 통합 조건

- `astro.bySolar`, `astro.byLunar`, `astro.withOptions`가 현재 진입점이다. 폐기 예정 별칭으로 새 코드를 작성하지 않는다.
- `astro.config`는 전역 설정이다. `withOptions`의 config도 전역 상태에 영향을 준다. 요청별 설정 변경을 허용하는 서버 구조로 연결하지 않는다. 번역 언어도 공유 상태이므로 운영 정책 확정 후 동일한 언어·설정을 일관되게 사용해야 한다.
- `Option` 타입에 시간대나 한국 달력 주입 옵션은 없다. `byLunar`도 내부 변환 후 `bySolar`를 호출한다. 날짜를 임의로 이동하거나 node_modules를 수정해 보정하지 않는다.
- `util.timeToIndex(hour)`가 이미 있다. 00시는 0, 01시부터 02시는 1, …, 21시부터 22시는 11, 23시는 12다. 입력 시각 검증·분 처리·시간 보정은 별도 책임이다.
- 유효하지 않은 양력 `2000-2-30`을 다음 달 날짜로 계산하며, 존재하지 않는 윤달 플래그도 무시되는 사례가 있다. 엔진 호출 성공을 입력 검증 성공으로 취급하지 않는다.
- 한국 달력 패키지 setter는 성공 여부를 boolean으로 반환한다. 실패 후 이전 상태가 남을 수 있으므로 변환마다 새 인스턴스를 사용하고 성공한 경우에만 getter를 읽어야 한다.
- 14주성만 표시하려면 별의 `type === 'major'`를 확인한다. 라이브러리 배열 이름만 보고 표시 범위를 확정하지 않는다.
- `soul`·`body`는 명주·신주이고, 명궁·신궁은 `earthlyBranchOfSoulPalace`·`earthlyBranchOfBodyPalace`다.
- 기본 직렬화(`toJSON`, `JSON.stringify`)가 제공되지만 출생일·성별·rawDates도 포함한다. 직렬화 결과를 공개 공유 응답으로 그대로 전달하지 않는다.

설치된 `iztro/lib/data/types/astro.d.ts`, `iztro/lib/astro/astro.js`, `iztro/lib/utils/index.d.ts`, `korean-lunar-calendar/dist/index.d.ts`와 실행 결과를 확인했다.

출처: [iztro 시작하기](https://iztro.com/en_US/quick-start), [전역 설정 문서](https://iztro.com/en_US/posts/config-n-plugin).

## 정책 상태

아래 엔진 기본값은 테스트 조건이며 사용자 확정 정책이 아니다.

| 항목           | 확인한 기본값 / 상태                                   | 출시 전 필요한 결정                                    |
| -------------- | ------------------------------------------------------ | ------------------------------------------------------ |
| 지원 지역      | 한국 출생자 확정                                       | 입력 화면에 범위 표시                                  |
| 입력 음력      | 한국 달력 기준으로 검증하는 설계안                     | 지원 연도와 공식 역서 경계 사례 검증                   |
| 명반 계산 음력 | iztro는 위 사례에서 중국 달력과 일치                   | 한국 음력 배치 또는 중국 달력 배치 중 근거를 갖고 선택 |
| 연도 경계      | yearDivide: normal (음력 설), exact는 입춘             | 채택 규칙 및 기준 명반 확보                            |
| 자시           | dayDivide: forward (늦은 자시 다음 날), current는 당일 | 23:00·00:00 경계 명반 검증                             |
| 윤달           | fixLeap: true, 15일까지 해당 월·16일부터 다음 월       | 채택 유파 규칙과 월말 사례 검증                        |
| 사화·별 배치   | algorithm: default, 사용자 정의표 없음                 | 독립 기준 명반으로 검증                                |
| 운한 관련      | ageDivide·horoscopeDivide: normal                      | 이번 출시 제외 설계안, 사용자 설정 UI 미구현           |
| 출생 시각      | 시간 미상·역사적 보정 미결정                           | 지원 연도, 표준시·서머타임·진태양시 정책 확정          |

한국 출생 전체를 고정 UTC+9로 처리한다고 가정하지 않는다. 라이브러리의 지원 연도 전체를 서비스가 검증한 범위로 표시하지 않는다.

## 검증과 한계

`src/domain/ziwei/engine-evaluation.test.ts`에 11개 평가 테스트를 추가했다.

| 근거                         | 확인하는 것                                                | 검증하지 못하는 것                   |
| ---------------------------- | ---------------------------------------------------------- | ------------------------------------ |
| iztro 공식 2000-8-16 예제    | 명궁·신궁·오행국·일부 주성 배치, 양음력 진입점 일치        | 독립적인 별 배치 정확성              |
| 한국천문연구원 2012년 자료   | 한국·중국 음력 4월 8일의 양력 차이                         | 자미두수 유파별 계산 규칙            |
| 한국 달력 패키지 2017년 예제 | 한국 윤달 입력 호환성 문제 재현                            | 별도 기관에 의한 2017년 검증         |
| 홍콩천문대 2023년 역표       | 윤2월 15·16일의 날짜                                       | 한국 역서 전 범위 일치               |
| 실제 설치 패키지의 동작      | 자시 전역 설정, 윤달 조정, 입력 오류 허용, 직렬화 개인정보 | 운영 입력 검증·동시 요청 안전성 구현 |

2023년 역표의 4월 5일·6일은 윤2월 15일·16일이다. 테스트에서 fixLeap 전후 배치 차이를 확인하지만 그 배치가 선택할 유파에 맞다는 독립 검증은 아니다.

출처: [홍콩천문대 2023년 역표](https://www.hko.gov.hk/en/gts/time/calendar/text/files/T2023e.txt).

전체 12궁·보조성·사화에 대한 독립 기준 명반은 아직 확보하지 않았다. 같은 엔진을 사용하는 서비스의 결과를 독립 정답으로 사용하지 않는다. 평가 테스트 통과는 **엔진 운영 채택 승인이나 계산 정확성 검증 완료가 아니다**.

## 다음 구현 순서

1. **계산 정책 확정**: 한국 음력 입력과 명반 계산 달력의 관계, 지원 연도, 시각 보정, 자시·윤달 규칙을 결정한다.
2. **독립 기준 명반 확보**: 일반 사례, 윤달 15·16일, 자시 전후, 연도 경계에 대해 출처·설정·예상 12궁과 별 배치를 기록한다.
3. **엔진 결정**: 한국 음력 배치가 필수라면 해당 달력을 지원하는 유지보수 가능한 엔진을 추가 조사한다. 현재 API에 없는 주입 기능을 추측하거나 날짜 우회 보정을 붙이지 않는다.
4. **최소 동작 흐름**: 승인된 정책의 입력 검증 → 명반 계산 → 기본 설명을 먼저 연결한다. 이어서 간편·상세 UI와 용어 설명을 구현한다.
5. **저장·해석·공유**: 보관·권한·해석 정책을 확정한 뒤 기능을 얹는다.

1~3의 정책·기준 자료가 없으면 계산 구현 완료 일정을 확정하지 않는다. 화면 작업과 독립적으로 진행 가능한 범위는 한국 출생 안내, 입력 접근성, 용어집 구조다.
