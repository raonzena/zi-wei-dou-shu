# 결과 보기 로딩 시간 개선

- 작성일: 2026-09-14
- 최종 갱신일: 2026-09-14
- 상태: 구현·로컬 검증 완료

## 작업 개요

출생 정보를 제출한 뒤 결과 화면이 나타날 때까지 오래 기다리는 원인을 확인하고, 개인정보 보호 정책을 유지하면서 줄일 수 있는 대기 시간을 개선한다. 명반 계산과 별 콘텐츠 조회를 병렬로 실행하고, 발행된 별 콘텐츠의 정상 조회 결과를 짧게 캐시하며, 운영 환경에서 남은 병목을 확인할 수 있도록 단계별 소요 시간을 기록한다.

## 요구사항

- REQ-02: 서로 독립적인 계산과 콘텐츠 조회를 동시에 시작한다.
- REQ-02: 정상 발행본만 5분 동안 캐시하고 조회 실패는 캐시하지 않는다.
- REQ-02, REQ-06: 운영 성능 로그에 이름, 출생 정보, 결과 ID, 소유 정보와 명반 내용을 남기지 않는다.
- REQ-06: 결과의 공개 링크, 소유 쿠키, 30일 보관과 만료 삭제 정책을 변경하지 않는다.
- 별 설명 콘텐츠 관리: 발행된 모든 버전과 출처 기록을 보존한다.

## 결정과 근거

- 운영 첫 화면을 확인했을 때 AI 해석은 비활성화되어 있었다. 따라서 현재 지연 원인에서 OpenAI 생성 시간은 제외했다.
- 유효 입력 한 건의 `calculatePreview` 테스트는 로컬에서 약 1.86초가 걸렸다. 이후 별 콘텐츠 조회, 결과 저장, 결과 페이지 조회가 순차로 이어지는 구조를 코드에서 확인했다.
- 이 프로젝트는 Next.js 16.3.4에서 Cache Components를 사용하지 않는다. 해당 버전의 로컬 공식 문서가 비 `fetch` 데이터 조회에 안내하는 `unstable_cache`를 사용하고 300초 후 다시 검증하도록 설정했다.
- 발행 실패나 네트워크 장애를 정상 콘텐츠처럼 캐시하면 복구 후에도 설명을 가져오지 못할 수 있으므로, 정상 조회만 캐시한다.
- 저장 직후 결과 페이지는 공개 UUID와 소유 쿠키를 기준으로 Supabase에서 다시 읽어야 한다. 이 조회를 생략하려면 결과 전달 방식과 권한 경계를 함께 바꿔야 하므로 이번 변경에는 포함하지 않고 소요 시간을 측정한다.

## 변경 내용과 영향

- `createSavedResult`가 명반 계산과 별 콘텐츠 조회를 `Promise.all`로 동시에 실행한다.
- 별 콘텐츠 정상 조회 결과를 5분 동안 서버 캐시에 보관한다. Supabase의 발행 이력과 저장 구조는 바꾸지 않는다.
- 결과 생성 로그에는 전체 시간과 계산, 콘텐츠 조회, 중복 판별, 저장, 선택적 AI 처리 시간을 기록한다.
- 결과 조회 로그에는 조회 결과, 소유자 확인 필요 여부와 소요 시간만 기록한다.
- 화면 문구, 결과 데이터 구조와 30일 보관 정책은 그대로 유지한다.

## 요구사항 대조

- 로딩 중 하단을 숨기는 기존 동작과 오류 문구는 변경하지 않았다.
- 결과 저장, 공개 조회, 소유자 판정과 30일 만료·삭제 정책은 변경하지 않았다.
- 캐시는 발행된 별 콘텐츠의 조회 결과만 대상으로 하며, `star_content`의 모든 버전 보관 정책을 변경하지 않는다.
- 운영 로그는 허용한 상태와 시간 값만 기록하며 개인정보와 결과 식별자를 제외했다.

## 남은 문제와 추후 개선점

- 저장 직후 결과 경로에서 동일한 결과를 한 번 다시 조회한다. 이 과정을 없애려면 URL 직접 방문과 새로고침, 소유자 판정, 서버 컴포넌트 렌더링을 함께 유지할 전달 구조가 필요하다.
- Vercel 콜드 스타트와 Supabase 저장·조회 중 어느 부분이 실제 운영 병목인지는 배포 후 단계별 로그로 확인해야 한다.
- 운영 측정 결과에서 저장 또는 조회가 주요 병목으로 확인되면 스냅샷 크기와 저장 프로시저를 별도 최적화한다.
