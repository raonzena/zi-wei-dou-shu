# 대체 계산 엔진과 한국 음력 기반 자체 구현 검토

- 작성일: 2026-09-11
- 최종 갱신일: 2026-09-11
- 상태: 조사 완료 / 엔진 선택과 계산 정책 미결정

이 문서는 엔진을 선택하기 전의 조사 기록이다. 후속 작업에서 초기 iztro 사용과 필요한 기능의 TypeScript 자체 구현 방향을 확정했다. 현재 정책은 [ADR-0003](../decisions/0003-engine-and-calculation-policy.md)을 따른다.

## 작업 개요

iztro 사용 필요성, 대체 라이브러리, 한국 음력 기반 명반 계산 프로젝트의 구현 가능성을 검토했다. 실제 엔진 제작·새 저장소 생성·패키지 교체는 이번 범위가 아니다.

## 요구사항

REQ-09의 지정 스택에 iztro는 포함되지 않는다. 요구사항 4절의 후보 기술이며 교체할 수 있다. REQ-01·10의 한국 출생 정보 지원과 OPEN-02의 계산 달력·배치 규칙 결정을 위한 조사다.

## 결정과 근거

### 후보 비교

| 후보                 | 공식 자료에서 확인한 내용                                       | 한국 음력 목표에 대한 판단                             |
| -------------------- | --------------------------------------------------------------- | ------------------------------------------------------ |
| MingPan (TypeScript) | package.json에 iztro ^2.5.0과 lunar-javascript 의존             | iztro 제거 목적의 대안이 아님                          |
| izthon (Python)      | iztro와 lunar-lite 동작 재구현, PyPI Alpha 표기                 | 언어 교체만으로 한국 달력 문제 해결 안 됨              |
| ziwei_core (Dart)    | 중국 UTC+8 달력 기준, 다른 달력에는 별도 어댑터 필요하다고 명시 | 확장 참고 후보, 즉시 한국 달력 지원으로 간주할 수 없음 |
| cdestiny (Python)    | 12궁·14주성·사화 등의 계산 API와 lunardate 의존                 | 별도 구현 참고 후보, 한국 달력 지원·정확성은 미검증    |

cdestiny의 문서상 기능·교차 검증 주장은 제작자의 설명이다. 이번에 테스트를 실행하거나 명반 정확성을 인증한 것이 아니다. cdestiny와 izthon은 Python 환경이 필요하고 ziwei_core는 Dart이므로 현재 TypeScript 앱에 도입하려면 별도 실행·연동 또는 이식 비용을 검토해야 한다.

이 후보들의 README, manifest, PyPI 배포 정보를 확인했으나 장기 유지보수 안정성을 판정할 충분한 근거는 확보하지 않았다. 이번 조사 범위에서는 한국 음력 기반 배치까지 검증되어 바로 도입할 수 있는 후보를 확인하지 못했다. 이것만으로 해당 라이브러리가 존재하지 않는다고 결론 내릴 수는 없다.

### 자체 구현 방향

한국 음력을 기준으로 명반을 배치하는 것이 목표라면, TypeScript 계산 코어를 직접 구현하고 관리하는 방향을 권장안으로 검토한다. 앞선 A안 권장은 기존 iztro 규칙을 받아들일 때만 적용된다. 라이브러리의 제약으로 제품 달력 기준을 먼저 정하지 않는다.

달력 천문 계산부터 재작성할 필요는 없다. 설치된 korean-lunar-calendar의 변환을 공식 역서 사례로 검증해 활용하고, 정규화한 한국 음력 연·월·일·윤달과 확정한 시각·간지 정책을 명반 코어에 전달하는 구조를 제안한다. 코어는 달력을 다시 변환하지 않고 입력으로 별과 궁의 배치를 계산한다. 결과는 UI·AI·DB와 독립된 구조 데이터로 반환한다.

구현 방법은 두 가지로 검토했다.

- 기존 iztro 소스를 바탕으로 필요한 본명반 계산 경로에서 달력 의존성을 분리한다. 코드를 많이 재사용할 수 있지만, 수정의 영향을 검증하고 원본 프로젝트의 변경을 추적해야 한다.
- 계산 규칙을 명세한 뒤 필요한 본명반 기능만 직접 구현한다. 구현 범위를 통제하기 쉽지만, 별 배치와 사화·밝기 등의 구현 및 검증을 직접 책임져야 한다.

재사용하는 코드·표·데이터는 해당 라이선스와 출처를 개별 확인한다.

확정 규칙과 기준 명반 없이 둘 중 하나를 최종 채택하지 않는다. iztro는 정책이 일치하는 사례의 비교 도구가 될 수 있지만 한국 달력이 다른 사례의 정답으로 쓰지 않는다.

## 구현 단계 제안

1. 지원 연도·시간 보정·자시·윤달·연도 경계·사화 규칙을 명세하고 출처와 독립 기준 명반을 확보한다.
2. 한국 달력 입력 검증·변환과 시간 정규화를 구현하고 경계 사례를 검증한다.
3. 12궁·명궁·신궁·오행국·14주성의 최소 계산부터 만들어 기본 화면에 연결한다.
4. 상세 화면에 필요한 보조성·사화·밝기 등 확정 항목을 추가한다. 3단계만으로 전체 결과 요구사항이 완료됐다고 처리하지 않는다.
5. 전체 출시 수용 사례를 검증하고 엔진·정책 버전을 결과에 기록한다.

처음부터 iztro의 운한·다국어·분석 API 전체를 구현하지 않는다. 모듈 경계는 처음부터 분리하되 패키지 배포와 별도 저장소는 실제 재사용·배포 요구가 있을 때 결정한다. 개발 일정은 규칙과 검증 자료를 확보한 뒤 작업량을 산정한다.

## 변경 내용과 영향

후보 조사와 자체 구현 제안을 이 페이지에 기록하고 작업 목록·요구사항 문서에 연결했다. 패키지 설치·제거 및 실행 코드 변경은 없다. 한국 음력 기준 명반을 최종 채택했다고 기록하지 않는다.

## 검증

2026-09-11 공식 저장소 README·manifest, PyPI 설명과 cdestiny 소스 파일을 열어 후보의 존재와 의존성을 확인했다. 대체 엔진 설치·실행·성능·전체 명반 정확성 검증은 수행하지 않았다. 문서 포맷·상대 링크·git diff --check를 검사하며, 코드 변경이 없어 앱 테스트·빌드는 재실행하지 않는다.

## 요구사항 대조

iztro 필수 사용 요구사항은 없으며 지정 기술 스택과 REQ-01~10을 유지한다. 자체 구현은 해결 가능한 방향의 제안이고 기능 축소가 아니다. 요구사항 수행 불가에 따른 변경은 없다. 상세 표시 항목과 계산 정책의 미결정 상태도 유지한다.

## 남은 문제와 추후 개선점

우선 한국 음력 기반 별 배치를 제품 기준으로 할지 결정하고 검증할 유파·규칙과 기준 명반 출처를 정해야 한다. 이후 재사용 가능한 소스의 달력 결합도와 테스트 품질을 비교해 소스 기반 수정 또는 직접 구현을 선택한다. 이번 후보 목록은 운영 채택 목록이 아니다.
