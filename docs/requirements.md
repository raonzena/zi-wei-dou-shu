# 요구사항 명세

최종 갱신일: 2026-09-12

상태: 사용자 확정 요구사항 + 구현 설계안

관련 문서: [화면 흐름](screen-flow.md), [기술 선택 기록](decisions/0001-technology-stack.md), [작업 기록](tasks/README.md)

이 문서는 현재 유효한 요구사항과 결정만 설명한다. 변경 전 상태와 결정 근거는 작업 문서, ADR, Git 이력에서 확인한다.

## 1. 제품 목표

자미두수에 익숙하지 않은 일반 사용자가 출생 정보를 입력해 간소화된 명반과 쉬운 한국어 해석을 확인하고, 필요하면 상세 명반을 탐색할 수 있도록 한다. 명반 계산과 자연어 해석의 책임을 분리한다.

첫 방문의 핵심 흐름은 **출생 정보 입력 → 계산·해석 준비 → 종합 풀이 → 상세 명반**이다. 결과는 30일간 저장하며 /result/[id] 링크로 복원한다. 링크를 아는 누구나 열람할 수 있고 결과 공유 버튼을 제공한다.

## 3. 화면별 수용 기준

### REQ-01 — 출생 정보 입력

- 생년월일, 양력·한국 음력, 음력 윤달 여부, 출생 시각, 계산에 필요한 성별을 입력받는다.
- 양력 연도는 1900년부터 현재 한국 연도까지, 음력 연도는 양력 1900년 생일 입력을 위해 1899년부터 지원한다.
- Brand를 누르면 `/`의 출생 정보 입력 화면으로 이동한다.
- 날짜·시각은 목록 선택과 직접 입력을 모두 지원한다. 입력 그룹 전체를 누르면 목록을 열고, 연도는 4자리, 월·일·시·분은 2자리까지만 받는다. 서버에서도 원본 입력의 자릿수를 검사한다. 성별은 남성을 기본 선택하고 출생 시각에는 기본값을 두지 않는다.
- 클라이언트와 서버에서 존재하지 않는 날짜, 지원 범위 밖 입력, 유효하지 않은 윤달, 미래 출생 순간을 검증한다.
- 대한민국의 역사적 표준시와 서머타임을 반영한다. 진태양시 보정은 적용하지 않으며 모호하거나 존재하지 않는 시각을 임의 계산하지 않는다.
- 출생 시각 미상 명반은 제공하지 않으며, 시각 모름 선택도 제공하지 않는다. 시·분 입력이 필요한 이유를 안내하고, 빈 입력을 임의의 시각으로 계산하지 않는다.
- 제출 중 중복 제출을 방지하고, 실패 후 입력 화면으로 돌아오면 현재 세션의 입력값을 유지한다.
- 입력 시점에 외부 AI 처리 범위와 운영 식별값·사용량 기록의 보관 범위를 안내한다.

### REQ-02 — 로딩과 오류

- 유효한 입력 제출 후 명반 계산과 AI 해석 준비 상태를 실제 작업에 맞게 표시한다.
- 임의의 진행률이나 연출을 위한 최소 대기 시간을 두지 않는다.
- 성공하면 종합 풀이로 이동하고, 계산·AI·네트워크 오류를 구분해 다음 행동을 제공한다.
- AI 실패 시 명반과 규칙 기반 기본 풀이는 유지한다.
- 일시적 오류에만 명시적 재시도를 제공하며 크레딧·설정·운영 한도 오류는 운영자 확인이 필요하다고 안내한다.
- 재시도 중 중복 요청과 입력 수정을 막고 기존 계산 결과는 계속 표시한다.

### REQ-03 / REQ-05 — 종합 풀이

- 상세 명반을 처음 열면 명반 도식의 왼쪽 상단(지지 사)에 있는 궁을 선택한다. 이 자리의 궁 이름은 출생 정보에 따라 달라지므로 복덕궁으로 고정하지 않는다. 상세 명반에서 선택한 궁은 탭을 오가도 유지한다. 종합 풀이의 명반은 선택 기능 없이 표시한다.

- 결과 탭의 이름은 ‘종합 풀이’와 ‘상세 명반’이다. 보기 모드를 지정하지 않은 첫 진입은 종합 풀이다.
- 12궁 관계를 유지한 간소화 명반 다음에 규칙 기반 기본 풀이와 활성화된 AI 해석을 표시한다.
- 종합 풀이에는 궁 이름, 14주성, 신궁, 오행국을 우선 표시한다.
- 종합 풀이에는 명반 도식을 유지하되 궁 선택 기능과 선택한 궁의 풀이 영역을 표시하지 않는다. 명궁 주성의 기본 풀이와 일곱 분야 종합 풀이, 활성화된 AI 해석은 유지한다.
- 명궁 주성의 기본 풀이 다음에 일곱 생활 분야의 종합 기본 풀이를 제공한다. 각 궁은 일반 사용자가 궁금해하는 질문을 제목으로 삼고 `별 또는 두 별 조합의 실제 성향 → 구체적인 생활 장면`을 중심으로 설명한다. 주성이 하나면 해당 별의 성향·강점·주의점을 설명하고, 둘이면 하나만 대표로 고르거나 개별 설명만 나열하지 않고 두 별이 함께 만드는 핵심 특징을 쉬운 말로 요약한다. `이 영역에서는`, `살펴봅니다`, `~해보세요`처럼 화면 구조를 해설하거나 행동을 반복해서 권하는 문장은 본문에서 사용하지 않으며, 생활 장면도 `예를 들어`라는 도입 없이 바로 설명한다. 명궁의 주성 풀이와 명궁을 맞은편 참고 궁으로 사용하는 영역에서는 같은 성향 문장과 위 기본 풀이를 가리키는 안내를 표시하지 않고 해당 생활 영역의 구체적인 장면만 설명한다. 열두 궁을 구분해 다루며 성찰 질문 목록은 표시하지 않는다.
- AI 결과는 전체 요약, 고정된 일곱 분야, 한 줄 요약 순서로 표시한다.
- 상세 보기로 이동해도 같은 명반과 해석을 재사용하며 AI를 다시 호출하지 않는다.

### REQ-04 — 상세 명반

- 종합 풀이와 동일한 계산 결과를 사용한다.
- 12궁, 간지, 주성, 검증 범위의 보조성·사화·밝기와 운한 계산 자료를 제공한다.
- 궁을 선택하면 주성별 의미, 주성이 둘일 때 두 별이 함께 만드는 특징, 해당 궁의 생활 영역에서 나타나는 모습, 일상에서 참고할 점, 별 목록 순서로 표시한다.
- 종합 풀이의 조합 요약은 쉬운 말로 간결하게 표시한다. 상세 명반은 `각 별의 의미 → 두 별이 함께 만드는 특징 → 해당 궁의 생활 영역에서 나타나는 모습` 순서로 설명한다. 각 항목은 7~8문장으로 풀어 쓰고, 근거에서 자연스럽게 이어지는 구체적인 생활 예시를 포함한다. 예시는 가능한 상황으로 제시하며 실제로 일어난 사건처럼 단정하지 않는다.
- 주성이 있는 궁은 해당 궁의 실제 주성만 사용한다. 주성이 없는 궁은 iztro 2.6.1의 명궁 주성 조회와 대궁 계산 방식을 기준으로 맞은편 궁의 주성을 참고하되, 본궁 주성처럼 표시하지 않는다. 선택 동작에서 재계산하거나 AI를 호출하지 않는다.
- 주성이 없으면 맞은편 궁 이름·참고한 주성과 해석 한계를 표시한다. 주성이 둘이면 iztro에서 확인한 실제 동궁 24개 조합의 두 별 기본 의미를 함께 반영한다. 밝기·사화·보조성까지 종합한 전문 풀이처럼 확대하지 않는다.
- 명반 판독 요약은 상세 화면에만 기본 접힘 상태로 표시한다.
- 두 보기 모두 명반을 읽는 방법을 안내한다. 읽기 안내는 상단 구분선과 여백을 둔 별도 섹션으로 표시한다. 상세 명반에서 ‘○○의 주성으로 읽는 나의 모습’은 접기 없이 항상 표시한다. 개별 주성·보조성의 별 설명은 기본 접힘 상태로 제공하며 출처를 표시한다.
- 새 출생 정보 입력으로 이동하는 버튼은 결과 하단 구분선 아래, 계산 기준 안내 위에 배치한다. 서버가 확인한 소유 정보(isOwner)를 사용해 생성 브라우저에는 ‘명반 다시 보기’, 그 외 방문자에게는 ‘나도 확인해보기’를 표시한다. 별도의 공유 쿼리나 경로는 만들지 않는다. 버튼과 계산 기준 안내 사이에도 구분선과 여백을 두어 별도 영역으로 구분한다.
- 정보가 많아도 명반 전체를 읽기 어려운 크기로 일괄 축소하지 않는다.

### REQ-06 — 공유

- 같은 브라우저의 소유 쿠키 안에서 정규화된 출생 시각·성별, 계산 정책·엔진·기준 시기, 기본 풀이·별 설명 버전과 내용, AI 사용 여부·모델·프롬프트가 같은 미만료 결과는 기존 ID로 재사용한다. 이름 입력은 이번 범위에서 추가하지 않으며 중복 판별에도 사용하지 않는다.
- 중복 판별값은 서버 비밀키 기반 HMAC으로 저장하고 원본 출생 정보나 판별값을 URL·로그·공개 응답에 넣지 않는다. DB의 고유 인덱스와 트랜잭션 잠금으로 동시 요청도 한 결과만 생성한다. 재사용 요청은 AI를 다시 호출하지 않는다.
- 재사용해도 기존 결과의 만료일은 연장하지 않는다. 만료 후에는 새 ID를 발급한다. 이전 결과는 만료 상태를 유지한다. 소유 쿠키가 달라지면 결과를 공유 재사용하지 않는다. 기존 저장 결과는 원본 입력이 없어 중복 키를 소급 계산하지 않는다.

- 두 보기의 공통 하단에 ‘결과 공유’ 버튼 하나를 제공한다. 공유와 다시 보기 버튼은 같은 크기·스타일을 사용하며, 태블릿·데스크탑에서는 같은 너비로 한 줄에, 모바일(640px 이하)에서는 두 줄에 배치한다. 데스크탑에서는 바로 링크를 복사하고, 태블릿·모바일 및 해당 기기의 앱 내 브라우저에서는 기기 공유를 연다. 기기 공유를 지원하지 않으면 링크를 복사한다. 사용자가 공유를 취소하면 오류나 자동 복사 없이 종료한다. 복사 완료는 페이지 디자인에 맞춘 토스트로 표시하고 4초 뒤 자동으로 닫는다. 반복 복사는 같은 토스트를 갱신하며 닫기 버튼과 스크린리더 안내를 제공한다. 공유·복사 권한이 없으면 직접 선택해 복사할 링크를 버튼 아래에 표시한다.
- 공유 링크에는 결과 ID와 현재 상세 보기 여부(view=detail)만 포함한다. 출생 정보·소유 자격 증명·기타 쿼리와 해시는 전달하지 않는다. 공유는 재계산·AI 호출·DB 변경 없이 동작한다.

- 결과를 Supabase에 저장하고 `/result/[id]`로 이동한다. 무작위 UUID를 사용하며 링크를 아는 누구나 저장된 결과를 열람한다. `/result/[id]?view=detail`은 상세 명반을 연다.
- 입력 전에 명반·풀이의 공개 범위와 30일 보관, 운한에서 출생 연도를 짐작할 수 있음을 안내한다. 원본 생년월일·시각·성별은 결과 저장소에 넣지 않는다.
- 계산된 명반·기본 풀이·AI 결과·계산 기준과 별 설명을 저장한다. 새로고침·링크 방문은 계산 엔진과 AI를 호출하지 않는다. 종합·궁별 풀이의 공통 설명 템플릿은 현재 배포 버전을 사용한다.
- 공개 조회와 소유자 권한을 분리한다. 실패한 AI 재시도는 생성 브라우저의 HttpOnly 쿠키로 확인한다. DB에는 자격 증명 원문 대신 해시만 저장한다. 쿠키 삭제 시 소유권 복구는 지원하지 않는다.
- 생성 후 30일이 지나면 조회를 차단하고 매시간 만료 결과를 삭제한다. 사용자 수동 삭제 기능과 결과 하단의 별도 보관·관리 안내는 제공하지 않는다. 보관 정책은 입력 화면에서 안내한다.
- 없는 링크·만료는 결과 없음으로 안내하고 저장소 장애는 다시 불러오기로 안내한다. 결과 페이지는 캐시·검색 색인을 허용하지 않는다.
- 원본 출생 정보는 저장하지 않으므로 두 버튼 모두 `/`의 새 입력 화면으로 연결한다. 생성한 브라우저라도 쿠키가 없으면 일반 방문자 문구를 표시한다. 진행 중인 계산 작업의 복원은 지원하지 않는다.
- 별도 공유 토큰·공유 전 확인 설계안은 사용자가 확정한 공개 결과 ID 링크로 대체한다. 입력 전 공개 안내를 제공하며, 별도 공유 해제는 후속 범위다.

## 5. 해석 정책과 품질

### 규칙 기반 기본 풀이

- 명궁과 상세 화면에서 선택한 궁의 주성을 바탕으로 기본 의미를 제공한다. 주성이 없으면 iztro 2.6.1이 명궁 주성 조회에서 사용하는 대궁 주성 참조와 동일한 위치 규칙을 적용하고, 종합 풀이의 다른 무주성 궁에도 그 규칙을 일관되게 사용한다.
- 각 별은 뜻을 바로 이해할 수 있는 특징 제목으로 표시한다. 주성이 하나면 종합 풀이에서 기본 모습과 균형점을 짧게 설명하고, 상세 명반에서 별의 의미와 생활 예시를 포함한 7~~8문장으로 설명한다. 주성이 둘이면 종합 풀이에서 두 별 조합의 핵심 특징을 쉬운 말로 간결하게 요약하고, 상세 명반에서 `각 별의 의미 → 두 별이 함께 만드는 특징 → 궁의 생활 영역에서 나타나는 모습` 순서로 각 항목을 7~~8문장으로 설명한다.
- 기본·종합·궁별 풀이의 성향 설명은 ‘태도로 읽을 수 있습니다’ 같은 우회 표현을 줄이고 ‘~하는 편입니다’, ‘~합니다’처럼 자연스럽게 쓴다. 상황에 따라 달라지는 반응이나 주의점의 가능성 표현은 유지하며, 미래 사건을 단정하는 의미로 바꾸지 않는다.
- 궁별 풀이는 전문 용어 중심 제목 대신 ‘어떤 생활 영역인지’, ‘나는 어떤 모습인지’, ‘생활에서 어떻게 활용할지’를 질문형 제목과 쉬운 문장으로 설명한다.
- 주성이 함께 놓이면 각 별의 의미와 두 별의 공통 강점·긴장·균형점을 구분한다. 주성이 없으면 맞은편 궁의 주성 기본 의미와 두 별 조합을 참고 풀이로 제공하며, 본궁의 주성이나 확정적인 종합 해석으로 소개하지 않는다.
- 개별 주성 설명과 종합 기본 풀이를 구분한다. 종합 기본 풀이는 열두 궁의 주성, iztro 2.6.1에서 확인한 24개 동궁 조합, 표시 범위의 발행된 보조성 설명, 생년사화와 원문에 명시된 천마·타라 및 경양·령성 동궁의 대비를 제공한다. 삼방사정은 비교할 배치 자료로 제공하며 연결 자체로 조언을 만들지 않는다. 쌍성의 밝기·사화·보조성을 결합한 학파별 전문 해석, 미지원 격국·궁간 사화 연쇄와 시기별 종합 풀이까지 구현된 것으로 표시하지 않는다.

### AI 명반 해석

- AI는 서버가 제공한 본명반 근거만 사용하며 명반 배치를 다시 계산하지 않는다.
- 응답은 `overview`, 고정 순서의 일곱 `sections`, `closing`으로 구성한다.
- 일곱 분야는 핵심 성향, 일과 커리어, 돈, 관계와 배우자, 내면과 삶의 방향, 건강과 컨디션, 가족·대인관계다.
- 전체 요약은 1~~2문단, 각 분야는 개인화된 제목과 두 문단으로 전체 7~~8문장을 제공하고 실제로 도움이 될 때만 짧은 목록을 사용한다. 각 분야에는 명반 근거에서 자연스럽게 이어지는 일상 예시를 최소 한 문장 포함하며, 실제 경험으로 단정하지 않는다. 문장 수는 품질 평가에서 확인한다.
- 마지막 문단은 ‘한 줄로 정리하면’으로 시작한다.
- 이전 12단계와 `terms`, `interpretation`, `check`, `step`, `monthly` 출력은 사용하지 않는다.
- 대한·유년·유월을 근거로 한 시기별 AI 운세는 제공하지 않는다. 서버 계산 자료는 상세 명반의 판독 요약에서 확인한다.
- 사용자에게 보이는 한국어는 다른 문체·분량 규칙보다 자연스럽고 이해하기 쉬운 표현을 우선한다. 주어와 뜻을 분명히 하고 번역투·명사 나열·불필요한 피동형·반복적인 해설 표현을 피한다. 전문 용어는 필요한 경우에만 문장 안에서 쉽게 설명한다. 직업·재물·관계·건강을 예언하거나 숙명적으로 단정하지 않는다. 명반에 근거한 “~일 수 있습니다” 정도의 경향·가능성 해석은 건강을 포함해 허용하되, 같은 종결 표현을 기계적으로 반복하지 않는다. 이를 확인된 사실이나 의료적 진단으로 제시하지 않는다.
- 아래 궁 연결·근거 설명·인용 대응 기준은 금전에 한정하지 않고 전체 요약, 일곱 분야의 제목·문단·조언 목록, 마무리 요약에 공통 적용한다. 기본 풀이에서는 성향·생활의 모습·조언을 쉽게 설명하고, 전문적인 배치와 연결 이유는 기본으로 접힌 ‘풀이 근거’에 분리한다.
- 다른 궁이나 사화 연결을 해석에 사용하면 해당 분야와 어떤 관련이 있고 해석에 어떻게 반영됐는지 ‘풀이 근거’에서 설명한다. 다른 궁으로 향하는 연결 자체를 금지하지 않는다.
- 명반을 근거로 조언할 때는 해당 배치를 어떤 경향으로 해석했고 그 경향에서 왜 해당 조언이 나오는지 설명한다. 연결의 수나 별의 일반적인 뜻만으로 결론을 대신하지 않는다. 충분한 설명은 전문 용어의 나열이 아니라 독자가 조언의 이유를 이해할 수 있는 설명을 뜻한다.
- 인용한 근거는 해당 문단의 해석과 대응해야 한다. 사용 이유를 설명하지 않은 근거는 인용 목록에서 제외한다. 각 문단의 중복 ID는 서버에서 첫 등장 순서를 유지하며 합치고 서로 다른 연결 설명은 보존한다. 중복만으로 전체 응답을 거부하지 않는다. 허용되지 않은 ID와 형식 오류는 계속 거부한다.
- AI는 제목·해석 문단·요약마다 `{text, evidence: [{id, relevance, interpretation}]}`를 생성한다. text는 쉬운 성향·생활 모습이며, relevance는 근거와 해당 주제의 관련성, interpretation은 그 관계로 성향을 어떻게 읽었는지 설명한다. 두 설명은 접힌 ‘풀이 근거’에 표시한다. 문자 일치나 전문 용어 반복은 요구하지 않는다.
- 행동 조언은 각 분야의 bulletPoints에만 `{text, paragraphId, reason}`으로 작성한다. 같은 분야의 실제 해석 문단(p1·p2·p3)을 참조하고, 그 문단의 어떤 성향에서 왜 조언이 나오는지 reason에 반드시 설명한다. 조언마다 별도의 근거 목록을 생성하지 않으며 제목·일반 문단·전체 요약·마무리에 조언을 섞지 않는다. 필요한 조언이 없으면 빈 목록을 허용한다.
- 다른 영역의 궁을 사용하는 경우 관련성을 특히 명확히 설명한다. 관련성을 설명할 수 없는 근거는 제외하고 설명 가능한 근거로 해석을 작성한다. 필드를 채웠다는 사실만으로 의미 타당성을 승인하지 않는다.
- 서버는 빈 근거·관련성·해석, 허용되지 않은 ID, 중복 문단 ID, 같은 분야에 없는 문단을 참조한 조언, 조언 이유 누락을 거부한다. 미성립 격국은 입력과 인용 후보에서 제외하고 실제 신궁 별칭을 제공한다. 배치 사실은 서버가 표시하므로 이름의 문자 포함 여부로 설명을 거부하지 않는다. 본문에 조언이 섞였는지와 설명의 타당성은 별도 의미 검토가 필요하다.
- 응답 구조, section 순서, 근거 ID, 사화 표현을 서버에서 검증한다. 내부 ID와 시기 근거 ID가 사용자 문장이나 새 AI 결과에 포함되면 거부한다.
- 구조 검증 통과를 의미적 정확성으로 간주하지 않으며 실제 기준 명반으로 별도 품질 평가를 수행한다.

### 별 설명 콘텐츠 관리

- 별의 뜻과 성향은 ‘별입니다’, ‘모습도 있습니다’, ‘~합니다’처럼 직접 설명한다. ‘~로 설명합니다’, ‘~으로 풀이합니다’, ‘~로 소개됩니다’처럼 해설을 전달하는 어투로 돌려 쓰지 않는다. 표현을 자연스럽게 바꾸더라도 기존 의미와 가능성의 범위를 유지하며 실제 사건을 확정하지 않는다.

- Supabase star_content에 별 식별자·언어·번역 버전, 원문 URL·Git 커밋·해당 구간, 한국어 설명, 번역 유형, 라이선스, 검수자·메모·시각과 발행 상태를 보존한다.
- 초안 → 검수 완료 → 발행 → 보관으로 관리한다. 일반 사용자는 발행본의 공개 필드만 조회하며 쓰기 권한과 검수 메모 조회 권한은 없다.
- 발행본은 직접 수정하지 않고 새 버전으로 검수·교체한다. 관리자는 Supabase 대시보드와 발행 함수를 사용한다. 별·언어마다 하나의 발행본만 허용한다.
- 상세 별 설명은 DB 발행본만 사용한다. 미발행은 검수 중, 조회 실패는 오류로 표시하며 파일 설명으로 대체하지 않는다. 새 페이지 요청에 최신 발행본을 반영한다.
- 초기 주성 14개·보조성 25개는 원문 대조를 거친 한국어 편집 설명이다. 전체 직역 또는 전문가 검수로 표시하지 않는다. 추가 전문 검수는 미완료다.
- AI는 같은 요청에서 읽은 발행본을 참고하며 원문·번역 버전을 중복 호출 식별에 포함한다. 알려진 별 이름이 본문 또는 조언 이유에 나오면 해당 문단의 인용 근거에 실제로 포함되어야 한다. 이 검사는 해석의 의미 타당성을 보장하지 않는다.

- SDK 요청 제한은 150초, Vercel 함수 제한은 180초이며 SDK 자동 재시도를 사용하지 않는다.
- main push는 GitHub Actions의 포맷·린트·타입·테스트·빌드 성공 후 Vercel production에 배포한다. PR은 검증만 수행한다.
- 서버 키는 클라이언트 번들, URL, 공유 메타데이터, 일반 로그에 포함하지 않는다.
- 모바일을 우선 설계하고 데스크톱·키보드 접근성을 함께 검증한다.

## 8. 출시 수용 시나리오

1. 유효한 출생 정보를 입력하면 로딩을 거쳐 종합 풀이과 해석이 표시된다.
2. 상세 탭으로 이동해도 동일한 결과이며 AI를 다시 호출하지 않는다.
3. 전문용어를 마우스·터치·키보드로 확인하고 닫을 수 있다.
4. AI가 비활성화되거나 실패해도 명반과 기본 풀이를 확인할 수 있다.
5. 운영 AI를 활성화하면 중복·횟수·예산 제한과 비용 기록이 동작한다.
6. 공유 구현 후 두 탭의 링크가 다른 브라우저에서 지정한 보기 모드로 열리고 비공개 정보는 노출되지 않는다.
7. 결과 만료 후 기존 결과 링크가 결과를 제공하지 않는다.
8. 기준 명반 테스트가 통과하며 채택 정책과 설명되지 않은 불일치가 있는 상태로 출시하지 않는다.

## 9. 문서 갱신 원칙

- 이 문서에는 현재 유효한 요구사항, 수용 기준, 미구현·미결정 상태만 기록한다.
- 새 결정이 기존 내용과 충돌하면 기존 문장을 최신 결정으로 교체한다. 날짜별 변경 절을 추가하거나 폐기된 결정을 함께 남기지 않는다.
- 변경 전 상태, 결정 이유, 검증 결과는 `docs/tasks/`, `docs/decisions/`, Git 커밋에서 확인한다.
- 구현 결과 때문에 요구사항을 임의로 낮추지 않는다. 사용자가 변경을 확정했거나 수행 불가 근거와 대안을 승인한 경우에만 현재 기준을 수정한다.
